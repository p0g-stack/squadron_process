# Launchers

A `ProcessLauncher` starts a place host: the app's own CLI in `serve` mode,
usually with more rights than the client has. The package ships a plain
launcher and one per OS elevation front-end; anything else (a privileged
helper the app already runs, a remote shell, a sandbox broker) is one more
implementation of the same interface.

| Launcher | Starts the host through | Sees stdout |
|---|---|---|
| `IoProcessLauncher` | `Process.start`, the caller's rights | yes |
| `PkexecLauncher` | polkit `pkexec` (Linux desktops) | yes |
| `SuLauncher` | `su -c` (rooted Android, other `su` setups) | yes |
| `MacAdminLauncher` | `osascript ... with administrator privileges` (macOS Authorization Services prompt) | no |
| `WindowsRunAsLauncher` | PowerShell `Start-Process -Verb RunAs` (UAC) | no |
| your own | whatever the embedding has | either |

`ElevatedLauncher.forHost()` picks the front-end for the OS it runs on.
Choosing a launcher by OS is fine; deciding what a place can *do* by OS is
not, that is what facts are for.

## What a launcher must do

1. Start `command.executable` with `command.arguments` exactly as given,
   applying `environment` and `workingDirectory` if it can (refuse the command
   if it cannot, as `WindowsRunAsLauncher` does for an environment).
2. Start it detached: the host must outlive the client's link and the
   launcher's own process or shell. It stops only by its lifetime rule (or a
   signal).
3. Return a `LaunchedProcess`: the host's stdout as lines if the launcher can
   see them (the first JSON line is the ready line), an empty stream if not;
   an `exitCode` that completes if the host exits early, or never.

## How the client finds the host

`ProcessPlace` appends `--launch-id <id>` to the command. The host echoes the
id in its ready line and in its session file (`--session-file`). The place
takes the first endpoint carrying that id, from stdout or by polling its
`EndpointStore`, so a stale session file from an older host is never used.
Front-ends that hide stdout therefore need a store; `FileEndpointStore` reads
the session file.

The session file holds the token. Put it in a directory only this user can
open: on POSIX a 0700 directory such as `$XDG_RUNTIME_DIR/<app>` or one made by
`Directory.systemTemp.createTemp` (mkdtemp); on Windows the user's own temp
directory. An elevated host can write there; other users cannot read it.

## Security notes

- The token is generated by the host (or read from `SQUADRON_PROCESS_TOKEN`)
  and never put on a command line, which other local users can read.
- The host binds 127.0.0.1 only and refuses a link whose hello has the wrong
  token; nothing else authenticates the client. An embedding that can check
  the peer (for instance the connecting socket's uid) can add that in its own
  launcher and host setup.
- The launch id is not a secret.
